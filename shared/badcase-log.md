# Badcase 追踪与修复机制

> 飞轮的燃料就是 badcase。每修一个 badcase，skill 就强一分。
> 最后更新：2026-09

---

## 什么是 badcase

凡是 AI 输出不符合预期的，都是 badcase。包括但不限于：

| 类型 | 举例 | 严重程度 |
|---|---|---|
| **事实错误** | 编造公司名、薪资数据、课程名称 | 🔴 严重（违反不编造原则） |
| **流程错误** | 转行门跳步了、没做 JD 调研就出计划 | 🔴 严重 |
| **格式错误** | 输出结构混乱、没有按要求的格式来 | 🟡 中等 |
| **内容偏差** | 学习计划重点不对、简历翻译不够精准 | 🟡 中等 |
| **体验问题** | 回答太啰嗦、语气不对、用户看不懂 | 🟢 轻微 |
| **遗漏内容** | 该输出的东西没输出全 | 🟢 轻微 |

---

## badcase 处理流程（4 步）

```
发现 → 记录 → 归因 → 修复 → 验证 → 沉淀
```

### Step 1：发现并记录

每次发现 badcase，立刻在 `badcase-log.md` 里加一条，格式：

```markdown
### [编号] [日期] [所属技能] 简短描述
- **严重程度**：🔴严重 / 🟡中等 / 🟢轻微
- **输入是什么**：用户说了什么、当时的上下文
- **AI 输出了什么**：有问题的输出是什么（贴关键部分）
- **预期应该是什么**：正确的输出应该是什么样的
- **发现人**：谁发现的
```

> 不需要写得很完美，先记下来再说。不记录 = 没发生。

### Step 2：归因分析

修之前先想清楚：**为什么会错？** 根因在哪？

| 根因分类 | 说明 | 修哪里 |
|---|---|---|
| **规则不明确** | skill 的 references 里没说清楚，AI 不知道该怎么做 | 补 skill 规则文档 |
| **知识库缺内容** | 知识库没有对应信息，AI 只能瞎编 | 补充知识库 |
| **AI 理解偏差** | 规则写了，但 AI 理解错了 | 改写规则，写得更直白，加例子 |
| **流程跳步** | 应该走的流程没走，直接出结果 | 加强流程约束，加门禁检查 |
| **用户输入模糊** | 用户说的不清楚，AI 理解错了 | 加澄清问题，先确认再输出 |
| **提示词太长溢出** | 上下文太长，前面的规则被冲掉了 | 精简内容、模块化加载 |

### Step 3：修复

根据归因结果，修对应的地方：

| 修什么 | 改哪里 |
|---|---|
| 规则不明确 | 对应 skill 的 `references/` 文档 |
| 知识库缺内容 | `assets/templates/knowledge-base/` 对应文件 |
| 流程跳步 | 对应 skill 的 SKILL.md 核心流程部分 |
| 容易理解偏差 | 加正反例、加"常见错误"板块 |
| 输出质量不稳 | 加输出自检清单（checklist） |

### Step 4：验证 + 沉淀

修复后要做 2 件事：
1. **验证**：拿原来的 badcase 输入再跑一遍，确认修好了
2. **沉淀**：把修复的内容记下来，以后遇到类似的不会再犯

## badcase 日志模板

```markdown
### [BC-001] [2026-09-03] [转行门] 用户问"你是谁"AI答错

- **严重程度**：🟡 中等
- **输入是什么**：用户导入 skill 后问"你是谁"
- **AI 输出了什么**："我是 Codex 助手"（没有切换到转行门身份）
- **预期应该是什么**："我是 Profession-ez 转行陪跑技能包里的转行门把关人…"
- **归因**：规则里写了但不够强，AI 没有优先采用 skill 设定的身份
- **修复方案**：在 SKILL.md 顶部加"⚠️ 激活前必读（强制）"，把身份说明放在最前面，加粗强调
- **修复状态**：✅ 已修复（v0.3.0）
- **验证结果**：已验证，导入后问"你是谁"，3 个平台均正确回答
```

## 修复优先级

| 优先级 | 类型 | 什么时候修 |
|---|---|---|
| P0 | 🔴 严重（编造事实/流程错误） | 立刻修，不修不能继续用 |
| P1 | 🟡 中等（内容偏差/格式错误） | 24 小时内修 |
| P2 | 🟢 轻微（体验问题/小遗漏） | 攒几个一起修，每周迭代 |

## 从 badcase 到知识库沉淀

不是所有 badcase 都只改规则——很多 badcase 反映的是知识库缺口。

**判断标准**：
- 如果是"AI 不知道 XX 知识" → 补知识库
- 如果是"AI 知道但用错了" → 改 skill 规则
- 如果是"AI 不知道该怎么做" → 补流程和方法论

**沉淀路径**：
```
badcase → 修复 → 有通用价值 → 进知识库
                    ↓
              是技能特有 → 进 skill references
```

## 定期复盘

建议每 2 周做一次 badcase 复盘：

1. 看看这段时间有哪些 badcase
2. 分类统计：哪类问题最多？（规则/知识库/流程/AI理解）
3. 找出根因：是系统性问题还是个别问题？
4. 规划下阶段修复重点

复盘结果写在 `badcase-log.md` 的顶部，格式：

```markdown
## 复盘记录

### [2026-09-15] 第 1 次复盘
- 总 badcase 数：X 个
- 分类：事实错误 X / 流程错误 X / 内容偏差 X / 体验问题 X
- 根因 TOP3：1. XXX  2. XXX  3. XXX
- 下次重点：XXX
```

## 铁律

1. **badcase 不是坏事**：发现一个修一个，每次修复 skill 都在变强
2. **不重复踩坑**：同一个 badcase 不能出现第二次。修完必须验证
3. **记录是第一步**：发现了先记下来，哪怕没时间立刻修。不记 = 白踩
4. **从 badcase 里找方向**：哪种 badcase 最多，说明哪个模块最薄弱，优先级最高
